# Industrial Visual Anomaly Detection Desktop - API Integration

## Purpose

This document defines how the Windows desktop client integrates with the existing Industrial Visual Anomaly Detection ASP.NET Core backend.

It records the client-side understanding of the verified HTTP contract. The backend repository remains authoritative when its published contract changes.

## Integration Boundary

The desktop application communicates only with the ASP.NET Core backend.

```text
WPF desktop client
        |
        | HTTPS, multipart form data, JSON and Problem Details
        v
ASP.NET Core backend
```

The desktop application must not:

- call the Python inference service directly;
- load model artifacts;
- reproduce backend image-signature validation;
- calculate the authoritative anomaly decision;
- assume access to backend or model filesystem paths.

## Client Components

Backend communication is isolated behind two application-facing service interfaces:

- `IBackendHealthService`, implemented by `BackendHealthService`, handles liveness and readiness;
- `IImageAnalysisService`, implemented by `BackendImageAnalysisService`, handles multipart image analysis.

Both implementations receive configured `HttpClient` instances through typed `IHttpClientFactory` registrations. `MainWindowViewModel` depends only on the service interfaces and does not construct HTTP requests or deserialize transport responses.

## Local Development Address

The verified backend development addresses are:

- HTTPS: `https://localhost:7056`;
- HTTP: `http://localhost:5070`.

The desktop application uses the HTTPS address by default for local development. The base address is configured through the `Backend` section of `appsettings.json` and is not duplicated in application code.

The local ASP.NET Core development certificate must be trusted. Production code does not disable TLS certificate validation.

## Endpoints

The desktop client uses:

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health/live` | Verify that the backend process responds. |
| `GET` | `/health/ready` | Verify that the backend and configured inference service are ready. |
| `POST` | `/api/v1/analyses` | Submit one image for anomaly analysis. |

The desktop client does not call the backend OpenAPI document during normal operation.

## Liveness

### Request

```http
GET /health/live
```

### Successful Response

Status: `200 OK`

```json
{
  "status": "healthy"
}
```

Liveness confirms that the backend process can answer requests. It does not prove that model inference is available.

## Readiness

### Request

```http
GET /health/ready
```

### Ready Response

Status: `200 OK`

```json
{
  "status": "ready"
}
```

### Not-Ready Response

Status: `503 Service Unavailable`

```json
{
  "status": "not_ready"
}
```

Readiness reflects whether the backend can reach its configured Python inference service and is ready to analyze images.

The client keeps liveness and readiness distinct. A live but not-ready backend is available for diagnostics but not operational for analysis.

## Health Workflow

The application performs one health refresh after startup and provides a manual refresh command. Liveness and readiness requests are made independently so the UI can represent partial availability.

Each health indicator supports:

- unknown before a check has started;
- checking while a request is active;
- available after a successful response with the expected status;
- unavailable after timeout, connectivity failure, or an unavailable response.

Continuous polling is not part of the initial implementation.

## Image Analysis

### Request

```http
POST /api/v1/analyses
Content-Type: multipart/form-data
```

The multipart form contains one required image part:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `image` | binary file | yes | PNG or JPEG image submitted for analysis. |

The multipart boundary is generated by .NET. The client does not set the complete `Content-Type` header manually when using `MultipartFormDataContent`.

The file part contains:

- field name `image`;
- original filename;
- media type derived for PNG or JPEG content.

The request stream and multipart content are disposed after the operation. The cancellation token is propagated through request sending and response reading.

### Successful Response

Status: `200 OK`

Example:

```json
{
  "model": {
    "id": "mvtec-ad-capsule-320",
    "category": "capsule"
  },
  "score": 4.992109298706055,
  "threshold": 2.501821517944336,
  "decision": "anomalous",
  "processingTimeMs": 1692,
  "traceId": "0HNNQ2F8C9UQT:00000001"
}
```

### Response Fields

| Field | Type | Meaning |
| --- | --- | --- |
| `model.id` | string | Identifier of the model configuration used for inference. |
| `model.category` | string | Industrial object category handled by the model. |
| `score` | number | Aggregated anomaly score. |
| `threshold` | number | Decision threshold selected during model export. |
| `decision` | string | Authoritative backend decision, currently `normal` or `anomalous`. |
| `processingTimeMs` | integer | Backend-measured processing duration in milliseconds. |
| `traceId` | string | Backend request trace identifier for diagnostics. |

`BackendImageAnalysisService` validates and maps the response into `ImageAnalysisResult`. The view model displays the supplied decision and supporting values without recalculating the decision from score and threshold.

The client tolerates unknown additional response properties to allow compatible backend evolution.

## Verified Upload Rules

The backend currently accepts:

- PNG images;
- JPEG images;
- files up to the configured upload limit, currently 10 MiB by default.

The backend validates:

- required multipart image presence;
- non-empty content;
- request and file size;
- declared media type;
- PNG or JPEG file signature;
- downstream image readability through the inference boundary.

The desktop file picker and preview loader provide early usability feedback, but backend validation remains authoritative.

## Error Contract

The backend uses Problem Details for analysis failures where applicable.

A response may contain fields such as:

```json
{
  "type": "about:blank",
  "title": "Invalid image",
  "status": 400,
  "detail": "The uploaded image could not be processed.",
  "traceId": "0HNNQ2F8C9UQT:00000002"
}
```

Exact titles and details may vary by failure. The desktop maps status and available response information rather than depending on one exact English sentence.

### Relevant Status Codes

| Status | Meaning for the desktop client |
| --- | --- |
| `400 Bad Request` | Missing, empty, malformed, or unreadable image input. |
| `413 Content Too Large` | Request or image exceeds the configured upload limit. |
| `415 Unsupported Media Type` | Declared or detected image type is not supported. |
| `503 Service Unavailable` | Backend inference dependency is unavailable, timed out, or returned an invalid response. |

Other non-success responses are handled safely as unexpected backend failures.

## Client-Side Failure Categories

The desktop client distinguishes presentation for:

- user cancellation;
- local file access or preview failure;
- backend validation or request failure;
- backend not ready;
- inference or service unavailability;
- HTTP timeout;
- connection failure;
- malformed or incompatible success response;
- unexpected HTTP failure.

Expected failures become clear view-model state rather than unhandled exceptions. Commands and busy state are restored after failure or cancellation.

## Trace Identifier Handling

The backend creates the authoritative trace identifier for each request. The desktop application:

- preserves `traceId` from successful analysis responses;
- displays it with the completed result for diagnostics;
- does not invent a replacement that could be mistaken for the backend trace identifier.

Trace information from future richer Problem Details mapping should be preserved where available. The desktop does not send its own correlation header in the initial version.

## Timeouts and Cancellation

The backend timeout is configured through `BackendOptions.TimeoutSeconds`. The same configured client boundary covers health and image-analysis calls.

Cancellation is propagated to the HTTP operation. The view model owns a cancellation source for the active analysis and exposes an explicit cancel command.

The client distinguishes:

- cancellation explicitly requested by the user;
- timeout caused by the configured HTTP deadline;
- connectivity or service failure.

## Serialization and Validation

The client uses `System.Text.Json` with explicit transport types inside the backend service implementation.

Response handling:

- accepts the backend camel-case JSON representation;
- tolerates unknown properties;
- validates required nested and scalar values;
- rejects unsupported decisions;
- rejects missing or incompatible result data;
- maps valid transport data into `ImageAnalysisResult` before updating UI state.

Partially valid transport data is not exposed as a successful result.

## HTTP Client Lifetime

Backend communication uses typed clients registered through `IHttpClientFactory`. The application does not create and dispose a new `HttpClient` for every operation.

The client registrations centralize:

- backend base address;
- request timeout;
- service implementation construction;
- lifetime management.

## Automated Verification

The HTTP integration layer is tested with controlled HTTP handlers rather than the real backend.

Current automated coverage includes:

- liveness and readiness response mapping;
- unavailable and timeout health behavior;
- multipart image request construction;
- successful normal and anomalous response mapping;
- invalid or incomplete response rejection;
- non-success response handling;
- cancellation and transport failures;
- view-model analysis and health state transitions.

The complete desktop suite currently contains 35 passing tests.

## Local Verification

With the backend running, liveness can be checked from PowerShell:

```powershell
curl.exe --insecure https://localhost:7056/health/live
```

Readiness can be checked with:

```powershell
curl.exe --insecure https://localhost:7056/health/ready
```

An image can be submitted with:

```powershell
curl.exe `
    --insecure `
    -X POST `
    https://localhost:7056/api/v1/analyses `
    -F "image=@C:\path\to\image.png;type=image/png"
```

`--insecure` is acceptable only for this manual local command when the development certificate is not trusted. The desktop application itself does not disable certificate validation.

## Verified End-to-End Results

The complete local chain has been verified with the Python inference service, ASP.NET Core backend, and WPF desktop client running simultaneously.

Verified examples using the exported `mvtec-ad-capsule-320` artifact:

| Image | Score | Threshold | Decision |
| --- | ---: | ---: | --- |
| Capsule `test/good/000.png` | `1.848755` | `2.501822` | `normal` |
| Capsule `test/poke/000.png` | `4.992109` | `2.501822` | `anomalous` |

The desktop displayed model identifier, category, processing duration, trace identifier, and the authoritative backend decision for both requests.

These examples verify integration behavior; they are not a new model benchmark.

## Future Contract Extensions

Possible later extensions include:

- heatmap availability or a heatmap resource endpoint;
- richer model metadata;
- analysis identifiers;
- analysis history;
- batch analysis;
- authentication.

The desktop client should not implement speculative fields before the backend exposes and verifies them.

## Current Integration Status

The complete initial integration is implemented and verified. The desktop client performs startup and manual health checks, submits PNG and JPEG images through the backend analysis endpoint, maps valid responses into application models, supports cancellation, and presents successful and failed operations as UI state.

Normal and anomalous image requests have both been verified end to end against the real local stack. Heatmap transport and other future contract extensions remain outside the current API integration.
